> 这是我在学习软件分析与设计时整理的系列笔记。概念部分是我按自己的理解写的，示例场景与图示都是自己编、自己画的。理解有偏差的地方欢迎指出。

## 0 「所有用户」是个陷阱

需求讨论里最常见的一句话是：「这个功能所有用户都会用到。」

问题在于，「所有用户」根本不存在。想省钱的家庭主妇、赶时间的商务客、替父母订票的年轻人，面对同一张订票页面，焦虑的点完全不同。为所有人设计，通常等于为没人设计。

范围界定（scoping）的第一步，就是**先做一次用户分群（user segment），再从里面挑出真正要服务的那几个**。

## 1 先把边界划出来

### 1.1 两份清单

在谈用户之前，先明确项目的边界，通常写成两个清单：

- **in scope（在范围内）**：这次要做的业务、角色、渠道；
- **out of scope（在范围外）**：这次明确不做的部分。

### 1.2 为什么 out of scope 更值钱

第二个清单比第一个更值钱。项目后期一半的争执，来自「这个当初是不是说了要做」—— 如果一开始就写清「本期不含退改签」，后面就不需要争。

边界与 scope boundary（范围边界）是同一个东西的两种叫法：它划的是**责任范围**，不是能力范围。

## 2 用户画像（Persona）：五个要素

### 2.1 五个要素

Persona（用户画像）是一个虚构但典型的用户档案。它的价值不在于「像真人」，而在于**让团队讨论需求时有一个具体的人可以指**。

一份有用的用户画像至少包含五个要素：

| 要素 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 目标 Goals | 他想达成什么？ | 顺利出行，不想多花冤枉钱 |
| 行为 Behaviors | 他现在怎么做这件事？ | 至少比 3 家，深夜看攻略，截图留证 |
| 环境 Context | 他什么时候、在哪、用什么做？ | 手机为主，通勤路上，网络不稳 |
| 痛点 Pain Points | 他在哪一步受挫？ | 价格不透明，条款难懂 |
| 限制 Constraints | 什么条件约束了他？ | 预算有限，年假固定，只看得懂中文 |

### 2.2 「行为」这一栏最容易写废

「行为」这一栏最容易被写废。常见的错误是把用户画像写成人口统计表：35 岁、女性、本科学历、年收入 8.5 万 —— 这些信息很难指导任何设计决策。**能指导决策的是行为：他上一次做这件事时的实际操作是什么样的。**

## 3 客户旅程图（Customer Journey Map）

### 3.1 一列里放什么

Persona 说清「他是谁」，Customer Journey Map（客户旅程图）说清「他经历了什么」。它把一件事拆成连续的**阶段（stage）**，每一列包含：

- **阶段** —— 产生念头 → 比较 → 下单 → 支付 → 出行后；
- **他在做什么** —— 具体动作；
- **他在想什么** —— 每个阶段的顾虑和疑问；
- **触点（touchpoint）** —— 他在哪个界面、渠道或人那里接触到你；
- **情绪（emotional curve）** —— 把每个阶段的感受高低连成一条线。

### 3.2 情绪曲线才是重点

最后那条情绪折线是整张图的重点。它把「哪里让人不爽」从模糊的感受变成**看得见的位置** —— 图上情绪最低的那一格，就是最值得先动手的地方。

在自建的订票例子里，情绪最低点在**下单**阶段：用户要填一堆信息，还不确定这些信息会不会被泄露。这比笼统地说「注册流程太长」有用得多，因为它明确指向了「信息量与信任感」这两个具体问题。

## 4 只挑关键的那一两个

用户画像不是越多越好。常见的做法是分**主要用户画像（primary persona）**和**次要用户画像（secondary persona）**：主要的那一个决定核心流程怎么设计，次要的只要求「不被妨碍」。

如果团队能画出五个同样重要的用户画像，通常说明还没有做出取舍 —— 访谈取样时要按类别挑代表性用户（representative user），而不是随手找最方便的人。

## 5 从这两样东西推到需求

### 5.1 从画像到需求的三步

有了 persona 和 journey map，往前推需求的路就清楚了，大致三步：

1. **找情绪最低点。** 定位到具体阶段与触点；
2. **问为什么低。** 回到用户的想法栏，例如「付款成功了吗」「凭证在哪」；
3. **写成可验证的需求假设。** 例如「用户在下单阶段的主要顾虑是信息安全 → 如果在这一步显示数据用途说明与安全承诺，放弃率会下降」。

第 3 步是这三步里唯一有交付价值的：**它同时写清了要做什么、以及怎么判断有没有效。**

## 6 常见的四个错误

- **把 persona 写成简历。** 堆人口统计信息，看不出行为特征，对设计没有帮助。
- **journey map 只有流程没有情绪。** 那它就退化成一张普通的流程图，失去了「哪里最痛」这个信息。
- **只画「应该发生」的旅程。** 旅程图要画用户**实际**怎么走，包括那些变通做法（workaround）—— 例如他为了确认价格，专门打电话又问了一遍。
- **画像和需求脱节。** 画完贴在墙上，后续文档再也用不到 —— 好的用法是让每条需求都能指回某个画像的某个痛点。

## 7 本节自测

1. 为什么「所有用户都会用」这句话对设计没有帮助？
2. in scope 和 out of scope 两份清单，哪一份在项目后期更有价值？为什么？
3. 用户画像的五个要素里，哪一栏最容易被写成无用信息？应该改成记录什么？
4. 客户旅程图里的情绪曲线解决了什么问题？
5. 把「用户觉得注册太麻烦」改写成一条可验证的需求假设。

## 8 术语表

| 术语 | 中文 | 一句话解释 |
| --- | --- | --- |
| scoping | 范围界定 | 明确本次做什么、不做什么 |
| scope boundary | 范围边界 | 划清系统与项目责任的那条线 |
| in scope / out of scope | 在范围内 / 范围外 | 本期要做 / 本期明确不做 |
| persona | 用户画像 | 虚构但典型的用户档案，用于讨论需求时指代具体的人 |
| primary persona | 主要用户画像 | 决定核心流程设计的那一个用户形象 |
| secondary persona | 次要用户画像 | 只需保证不被妨碍的用户形象 |
| user segment | 用户分群 | 按特征把用户划分成若干群体 |
| customer journey map | 客户旅程图 | 把用户完成一件事的阶段、动作、想法与情绪画在一起 |
| stage | 阶段 | 旅程图上的一列，表示旅程中的一个环节 |
| touchpoint | 触点 | 用户与产品、服务或人员发生接触的位置 |
| emotional curve | 情绪曲线 | 把各阶段的情绪高低连成的线，用来定位最痛的位置 |
| pain point | 痛点 | 用户在当前流程中受阻或不满的地方 |
| representative user | 代表性用户 | 能代表某一类用户的关键个体，常用于访谈取样 |
| workaround | 变通做法 | 用户绕开现有流程问题的临时手段 |
