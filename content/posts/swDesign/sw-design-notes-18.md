> 这是我在学习软件分析与设计时整理的系列笔记。概念部分是我按自己的理解写的，示例与图示都是自己编、自己画的。理解有偏差的地方欢迎指出。

## 0 直接建表会出什么问题

需求刚谈完，最自然的下一个动作就是打开数据库工具开始建表。但这个顺序会带来三类麻烦：

- **字段名各写各的。** 同一个人名，有的表叫 `name`，有的叫 `custName`，有的叫 `c_name`；
- **关系靠猜。** 「一个订单能有几个收货地址」没人问过，开发按自己的理解建了外键；
- **类型和长度随手定。** 电话字段给了 10 位，结果来了个带区号的号码。

数据库分析（database analysis）就是把这三件事在动手之前先确定下来：**有哪些实体、它们之间是什么关系、每个字段叫什么、什么类型、什么业务规则。**

顺带明确一下**数据库管理系统（DBMS）** 的位置：它位于应用和数据库之间，负责数据的检索与更新（关系型的那一类通常缩写为 **RDBMS**）。应用不直接碰文件，而是通过它来读写数据。

## 1 数据模型与实体关系图

### 1.1 三个元素与判断要点

数据模型（data model）在这个阶段就是用**实体关系图（entity relationship diagram, ERD）** 表达的。它由三样东西组成：

| 元素 | 含义 | 判断要点 |
| --- | --- | --- |
| 实体（entity） | 业务中可区分的对象 | 能被唯一标识，且有多个实例 |
| 关系（relationship） | 实体之间的业务关联 | 关系本身描述的是业务动作或约束 |
| 属性（attribute） | 实体上需要记录的信息 | 来自需求，不是为了方便而加 |

### 1.2 实体和一般名词的分界线

「能被唯一标识」这个条件是实体和一般名词的分界线。像「红色」这种属性值，本身不能单独成为一个实体。

## 2 基数必须由业务方确认

### 2.1 一对一、一对多、多对多

**基数（cardinality）** 是关系两端各自可以有多少个实例。图上写的是 `1` 和 `*`，背后对应的是业务规则：

- 一个客户可以有多张订单 → 客户端是 `1`，订单端是 `*`；
- 一张订单可以包含多个商品，一个商品可以出现在多张订单里 → 两端都是 `*`。

第二例就是**多对多**。它在关系模型里没法直接落地，通常要拆出一个中间实体（例如 `ORDER_ITEM`），这一点在设计阶段处理。

### 2.2 基数不要自己假设

这里有条纪律值得单独强调：**基数不要自己假设，一定要去问。**「一个订单能不能拆单」「一个客户能不能有多个联系人」——这类问题只有业务方能回答，猜错的话，改起来要动数据、动代码、动报表。

### 2.3 还要确认可选性

另外还有一端需要确认：**关系的可选性（optionality）** —— 这一端是必须存在（`1`），还是可以没有（`0..1`）。这决定了字段是否允许为空。

## 3 属性分析与数据命名

### 3.1 属性归属

属性分析（attribute analysis）要回答的是：每个实体上到底有哪些属性、它们属于谁。

这里的第一道坎是**属性归属**：`customer_name` 该放在订单上，还是放在客户上？判断标准是**依赖关系** —— 一个客户的姓名，跟他下几次单无关，所以它属于客户。放在订单上就会重复存储（这正是笔记 19 要解决的问题）。

### 3.2 命名标准

第二道坎是命名。**数据命名标准（data naming standard）** 通常包含这些规则：

- 实体名用单数名词（`CUSTOMER`，不是 `CUSTOMERS`）；
- 属性名带上实体前缀（`customer_name`、`order_date`），避免在跨表查询时产生歧义；
- 统一用下划线分隔，不用驼峰或空格混用；
- 名称里避免出现项目缩写（半年后没人记得 `tmp_flg` 是什么）。

### 3.3 类别关键字

还有一类元素叫**类别关键字（class keyword）**：用来区分同一属性的不同类别，例如状态字段 `order_status` 的取值集合。它的作用是把「这个字段能取哪些值」集中记录在一处，而不是散落在代码里。

## 4 数据字典

### 4.1 四列结构

把上面这些汇总成一张表，就是**数据字典（data dictionary）**：

| 列 | 内容 |
| --- | --- |
| ATTRIBUTE NAME | 属性名，按命名标准 |
| TYPE | 数据类型（data type） |
| LEN | 长度（length） |
| DEFINITION AND BUSINESS RULES | 定义与业务规则（business rule） |

### 4.2 最值钱也最常空着的一列

第四列是整张字典里最值钱的一列，也是最常被空着的一列。它要写的是「这个字段在业务上意味着什么、有什么约束」：

- `customer_id`：系统自动生成，不可修改；
- `contact_no`：仅允许 8–20 位数字；
- `join_date`：不得晚于当前日期。

这些规则如果只留在需求文档的正文里，开发很可能漏掉；写进数据字典，它就和字段绑在一起了。

## 5 键（key）

### 5.1 五种键

标识一个实体实例用的信息，统称标识符（identifier），落到表上就是各种键：

- **主键（primary key）** —— 唯一标识一行，不允许重复、不允许为空；
- **简单键（simple key）** —— 由单个属性构成，例如 `order_id`；
- **复合键（composite key）** —— 由多个属性共同构成，例如订单明细表的 `order_id + item_no`；
- **人工键（artificial key）** —— 业务本身没有合适的唯一标识时，人为加一个编号（例如流水号）；
- **外键（foreign key）** —— 指向另一个表主键的字段，用来表达关系。

### 5.2 实体与实体实例

最后补充一个术语：**实体实例（entity occurrence）** —— 实体是「客户」这个概念，而「张三这个客户」是一个实体实例。主键要保证的正是**每个实体实例都能被唯一标识**。

## 7 术语表

| --- | --- | --- |
| database | 数据库 | 结构化保存数据的集合 |
| DBMS | 数据库管理系统 | 位于应用与数据库之间、负责读写数据的软件 |
| RDBMS | 关系型数据库管理系统 | 以表与关系组织数据的 DBMS |
| data model | 数据模型 | 描述数据结构的模型 |
| entity relationship diagram（ERD） | 实体关系图 | 画出实体、关系与基数的图 |
| entity | 实体 | 业务中可区分的对象 |
| entity occurrence | 实体实例 | 实体的一条具体记录 |
| relationship | 关系 | 两个实体之间的业务关联 |
| cardinality | 基数 | 关系两端各自可以有多少个实例 |
| optionality | 可选性 | 关系的一端是否必须存在 |
| attribute | 属性 | 实体上需要记录的信息项 |
| attribute analysis | 属性分析 | 确定属性有哪些、属于哪个实体 |
| data naming standard | 数据命名标准 | 全项目统一的字段命名规则 |
| class keyword | 类别关键字 | 用来区分属性取值类别的标记 |
| data dictionary | 数据字典 | 逐字段记录名称、类型、长度与业务规则的清单 |
| data type | 数据类型 | 字段存储的数据种类 |
| length | 长度 | 字段允许的最大长度 |
| business rule | 业务规则 | 字段在业务上必须满足的约束 |
| identifier | 标识符 | 能唯一区分实体实例的信息 |
| primary key | 主键 | 唯一标识一行的字段组合 |
| simple key | 简单键 | 由单个属性构成的主键 |
| composite key | 复合键 | 由多个属性共同构成的主键 |
| artificial key | 人工键 | 业务无天然标识时人为引入的编号 |
| foreign key | 外键 | 指向另一张表主键的字段 |
