## 0 同一句话，两种改法

需求方说：「我们要新增一类客户，价格政策不一样。」

这句话在不同设计下的代价完全不同：

- **设计 A**：改一个文件里的一个 `if`；
- **设计 B**：改三个文件，其中两个是别人负责的；改完还要回归测试五个功能。

这两者之间的差别，就是这一篇要讲的**设计原则（design principles）**。

## 1 衡量设计的两个词

![设计原则里的内聚与耦合，以及抽象类与接口的选择依据：内聚衡量模块内部元素的相关程度，耦合衡量模块之间的依赖程度；共享实现用抽象类，只约定行为用接口，跨领域组合也用接口](/images/sw-design-notes-24-design-principles.svg)

### 1.1 内聚（cohesion）

**内聚（cohesion）** 说的是一个模块内部各元素的相关程度。

- 内聚高：这个类只做一件事，它的所有方法都在服务同一份数据；
- 内聚低：一个类里塞了几件不相关的事，改 A 的时候要担心弄坏 B。

### 1.2 耦合（coupling）

**耦合（coupling）** 说的是模块之间的依赖程度。

- 松耦合（loosely coupled system）：一方改动，另一方不用跟着改；
- 紧耦合：改一处要顺着调用链改一路。

### 1.3 好设计的标准

好设计（good design）的标准由此推出来：**高内聚、低耦合**。这个说法很常见，但它的实际含义是具体的 —— 高内聚让「改动集中」，低耦合让「改动不外溢」。

顺带一提，可维护性（ease of maintenance）和可扩展性（extensibility）不是另外两个维度，它们是好内聚耦合的**结果**。

## 2 一次完整的重设计

### 2.1 一个具体的坏设计

看一个具体的坏设计。假设价格政策写在客户类里：

```java
class Customer {
    private String type;      // "VIP" / "CORPORATE" / "NORMAL"
    private int creditLimit;  // 只有企业客户用得上
    private String taxNo;     // 只有企业客户用得上

    double discount() {
        if (type.equals("VIP")) return 0.2;
        if (type.equals("CORPORATE")) return 0.15;
        return 0.0;
    }
}
```

它有三个问题：

1. **内聚低。** `creditLimit`、`taxNo` 只对企业客户有意义，却塞在所有人共用的类里；
2. **耦合高。** 每种新的客户类型，都要回来改这个类。改这个类的人可能同时在改别的地方；
3. **判断分散。** 折扣的逻辑在这里，其他针对类型的判断可能散落在别处。

### 2.2 用多态重设计

用多态重设计之后：

```java
abstract class Customer {
    abstract double discount();
}

class VipCustomer extends Customer {
    double discount() { return 0.2; }
}

class CorporateCustomer extends Customer {
    private int creditLimit;
    private String taxNo;
    double discount() { return 0.15; }
}
```

变化发生了：

- 类型专有的数据（`creditLimit`、`taxNo`）**移到了真正用它的子类里** → 内聚提高；
- 调用方只写 `c.discount()`，不需要知道有哪几种客户 → 耦合降低；
- 新增一种客户 = 新增一个类，**已有的代码一行都不用改**。

这个「通过继承与抽象方法让对象自己回答」的做法，就叫**面向多态的设计（design for polymorphism）**。

## 3 抽象类与接口怎么选

### 3.1 四种情形对应用什么

重设计之后马上会遇到下一个问题：父类该是**抽象类（abstract class / abstract superclass）**，还是**接口（interface）**？

| 情形 | 用什么 |
| --- | --- |
| 多个类要共享同一部分实现（不只是接口） | 抽象类 |
| 只约定行为，不共享任何实现 | 接口 |
| 这些类分属不同领域，只是恰好都需要这个能力 | 接口 |
| 一个类需要同时具备多种能力 | 多个接口 |

### 3.2 几条补充判断

几条补充的判断：

- **抽象父类**和**具体父类（concrete superclass）** 的差别在于能不能被直接实例化。如果父类本身没有实际意义（「客户」永远是某种具体的客户），就该是抽象类；
- 反过来，如果父类确实有实例（「普通客户」就是一种真实的客户类型），那用**具体类（concrete class）** 作父类也没问题 —— 不要为了「看起来更抽象」而强行抽象；
- 单继承语言里，「同时具备多种能力」只能靠多接口实现，这也是接口在这种语言里格外重要的原因。

## 4 复用：机会与陷阱

### 4.1 值得先找一遍的复用机会

设计原则里还有一条是关于**可复用性（reusability）** 的：主动寻找可以复用的组件，而不是每次重写。

值得先找一遍的**复用机会（reuse opportunity）** 通常是横切性的东西：

- 数据访问（笔记 23 的数据代理）；
- 日志与审计；
- 参数校验与权限检查；
- 统一的错误处理。

### 4.2 复用并不总是好的

但复用有个反直觉的地方：**它并不总是好的。**如果两段代码只是看起来相似，而变化的时机不同，把它们强行合并成一份，反而会制造耦合 —— 将来其中一方要改，另一方会被迫跟着改，甚至要加参数来区分「你现在是哪种情况」。

判断标准是那句老话：**它们会一起变化吗？**会一起变的，该合并；只是碰巧长得像的，别合并。

## 5 三条能立刻用的自查

- **加一个新类型，要改几个文件？** 改得越少越好。理想情况是只加文件、不改文件；
- **改一个字段名或一条规则，要改几个地方？** 超过两处，说明这个信息被复制了；
- **这段代码，新同事多久能看懂它为什么这么写？** 如果需要翻三个历史提交才能理解，说明结构本身在传达错误的信息。

## 6 本节自测

2. 在那一节的坏设计里，`creditLimit` 为什么该移到子类里？
3. 什么情况下该用抽象类而不是接口？什么情况下该用接口？
4. 为什么「看起来相似」不足以成为合并代码的理由？
