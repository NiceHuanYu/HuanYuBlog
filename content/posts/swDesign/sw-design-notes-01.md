> 这是我在学习软件分析与设计时整理的系列笔记。概念部分是我按自己的理解写的，场景与图示都是自己编、自己画的，参考的主要是 UML 规范、敏捷宣言、Scrum Guide、ER 模型与规范化相关的公开文献这类一手资料。理解有偏差的地方欢迎指出。

## 0 先说清楚这门课要解决的问题

### 0.1 三句没法直接开工的话

只要参与过一点实际项目，大概都听过这几句话：

- 「需求先做起来，细节以后再补。」
- 「这里加个按钮就行。」
- 「性能要快。」

这些话没法直接开工，因为它们都缺同一样东西：**可以被验证的判断标准**。

### 0.2 三个要回答的问题

所谓软件分析与设计，就是把这类模糊的期望，一步步变成有边界、可验证、能被实现的东西。整个过程可以拆成三个问题：

1. **要做什么** —— 需求从哪里来？谁说了算（也就是利益相关者，stakeholder）？怎么判断它真实、完整、在范围内？
2. **怎么表达** —— 用什么模型把需求写清楚，让用户、分析师、开发看到的是同一件事？
3. **结构怎么定** —— 这些模型怎么变成能写代码、能建表、能长期维护的结构？

后面 25 篇笔记，都是围绕这三个问题展开的。这一篇先把地图铺开。

## 1 主干链路：从需求到设计

<img src="/images/sw-design-notes-01-main-path.svg" title="" alt="从需求到设计的主干链路：第一阶段把需求变成模型，包含事实调查、范围界定、用户故事、用例建模、实体与工作流、前端设计、非功能需求、测试；第二阶段把模型变成软件结构，包含数据库分析与 ERD、规范化、逻辑数据模型、面向对象概念、UML 类图与顺序图、分析建模、设计建模、设计原则、重构" width="766" />

这张图是整份系列的骨架。它有一条重要性质：**每一环的输出就是下一环的输入**。

### 1.1 第一阶段的九个环节

- 事实调查（Fact Finding）产出的是访谈记录、观察结论这类原始材料；
- 范围界定（Scoping）把这些材料收成「做什么、不做什么」；
- 用户故事（User Story）把范围拆成一条条能验收的语句；
- 用例建模（Use Case Model）再把用户故事翻译成「谁、在什么条件下、对系统做什么」，一个用例下通常还挂着几条具体走法（scenario）；
- 活动图（Activity Diagram）把用例的流程画到能看清分支和例外；
- 实体与工作流（Entity / Workflow）从流程里抽出业务概念，形成领域模型（Domain Model）；
- 前端设计（UI / UX Design）把流程落到具体的界面与屏幕流程；
- 非功能需求（Non-Functional Requirement, NFR）补上「做得多好」；
- 测试（Testing）给出「怎么证明它做到了」。

### 1.2 第二阶段的八个环节

第二阶段换了一个视角：

- 数据库分析（Database Analysis）把业务概念变成实体、关系与基数（Cardinality），最后画成实体关系图（Entity Relationship Diagram, ERD）；
- 规范化（Normalization）把表结构调整到减少冗余、避免更新异常；
- 逻辑数据模型（Logical Data Model, LDM）在第三范式之上补出完整的关系；
- 面向对象（Object Orientation）提供另一套组织方式：对象、类、封装、继承、多态；
- UML 的类图（Class Diagram）与顺序图（Sequence Diagram）是这套方式的表达工具；
- 分析建模（Analysis Modelling）回答「每个用例由哪些对象协作完成」；
- 设计建模（Design Modelling）回答「这些对象怎么落到数据库、数据访问层和框架上」；
- 设计原则（Design Principles）与重构（Refactoring）负责让结构长期不烂。

## 2 两个阶段分别在做什么

|          | 第一阶段 · 需求与分析                                                  | 第二阶段 · 设计与结构                                             |
| -------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 核心问题 | 这个系统为谁解决什么问题                                               | 这个系统怎么组织成能实现的代码与数据                              |
| 主要动作 | 获取、界定、建模、确认                                                 | 抽象、映射、取舍、整理                                            |
| 典型产出 | 用户画像、客户旅程图、用户故事、用例模型、活动图、领域模型、非功能需求 | ERD、逻辑数据模型、类图、顺序图、分析模型、设计模型、重构后的代码 |
| 由谁验收 | **用户/业务方能不能看懂并确认**                                        | **开发能不能直接照着实现**                                        |
| 出错代价 | 做出来的东西没人用                                                     | 能跑，但改不动                                                    |

最后两行是我自己的总结，也是这份笔记反复会回到的判断口径：**需求阶段用「用户能不能确认」验收，设计阶段用「开发能不能实现」验收**。很多项目出问题，是拿错了尺子 —— 比如用「代码能跑」去验收需求。

## 4 一个完整交付物里有什么

### 4.1 九项交付物清单

一门分析与设计课程最后要交的东西，通常叫用户需求规格说明书（User Requirement Specification, URS）—— 其实就是把上面那些环节的产出装订在一起。清单大致固定：

1. **访谈脚本与访谈记录** —— 你问了什么，对方怎么答；
2. **关键用户画像 + 客户旅程图（Customer Journey Map）** —— 你选定的代表性用户是谁，他走完一件事要经过哪些步骤、在哪里受挫；
3. **一组用户故事** —— 通常 10 条左右，覆盖主流程；
4. **用例模型** —— 系统的功能边界，参与者（Actor）与用例（Use Case）的对应关系；
5. **活动图** —— 每个重要用例一张，包含分支与例外；
6. **屏幕设计** —— 关键用例的界面草图与页面之间的跳转；
7. **非功能需求** —— 性能、安全、可靠性；
8. **测试用例与测试数据** —— 不止一条，要覆盖异常输入；
9. **一份面向决策者的提案** —— 讲清楚现状问题、引入的技术、以及对用户的理解。

这份清单可以直接当自查表用：哪一项写不出来，说明对应的环节没做到位。

## 5 这份系列笔记的固定结构

### 5.1 每篇的固定骨架

为了让你能按节奏跟踪，每篇都是同一套骨架：

- **开头**：这一环要解决什么具体麻烦（从场景讲起，不从定义讲起）；
- **中间**：概念、判断标准、可操作的做法，配自绘图示；
- **例子**：全部是自己编的场景，用「某在线旅行社」「某连锁超市」这类虚构对象；
- **末尾**：`本节自测`（3–5 题）+ `术语表`（英文 | 中文 | 一句话解释）。

### 5.2 术语的写法约定

专业英语名词第一次出现时写作 `English（中文）`，之后统一用英文，方便你在读英文文档和 UML 工具时对得上号。

## 6 本节自测

1. 需求阶段和设计阶段，「做完了」的验收标准有什么本质区别？
2. 「系统要快」为什么不能算一条合格的需求？要补上哪些信息才成立？
3. 用户画像（persona）和用户故事（user story）是什么关系？
4. 用例模型（use case model）和活动图（activity diagram）分别回答什么问题？
5. 一份交付物里同时有 ERD 和类图，它们的关注点差别在哪？

## 7 术语表

| 术语                                  | 中文               | 一句话解释                                     |
| ------------------------------------- | ------------------ | ---------------------------------------------- |
| requirement                           | 需求               | 系统必须满足的条件或必须具备的能力             |
| functional requirement                | 功能需求           | 系统要「做什么」                               |
| non-functional requirement（NFR）     | 非功能需求         | 系统「做得多好」，如性能、安全、可靠性         |
| scoping                               | 范围界定           | 明确哪些进范围、哪些明确不做                   |
| fact finding                          | 事实调查           | 访谈、观察、问卷等获取需求手段的总称           |
| stakeholder                           | 利益相关者         | 对系统有影响或被系统影响的角色                 |
| actor                                 | 参与者             | 与系统交互的外部角色，可以是人也可以是外部系统 |
| use case                              | 用例               | 一个参与者通过系统达成某个目标的过程           |
| scenario                              | 场景               | 用例的一条具体走法                             |
| activity diagram                      | 活动图             | 描述流程步骤、分支与并行的图                   |
| persona                               | 用户画像           | 一个虚构但典型的用户档案                       |
| customer journey map                  | 客户旅程图         | 用户完成目标的步骤、触点与情绪记录             |
| user story                            | 用户故事           | 从使用者视角描述一条功能的一句话               |
| domain model                          | 领域模型           | 业务概念及其关系的模型                         |
| entity relationship diagram（ERD）    | 实体关系图         | 数据实体、关系与基数的图形表示                 |
| cardinality                           | 基数               | 关系两端各自可以有多少个实例                   |
| normalization                         | 规范化             | 按规则调整表结构，减少冗余与更新异常           |
| logical data model（LDM）             | 逻辑数据模型       | 规范化之上、补齐关系的详细数据模型             |
| class diagram                         | 类图               | 用类、属性、操作与关系描述静态结构             |
| sequence diagram                      | 顺序图             | 用对象之间的消息往来描述交互，纵向是时间       |
| analysis modelling                    | 分析建模           | 把用例分摊到协作的对象上                       |
| design modelling                      | 设计建模           | 把对象模型落到数据库、访问层与框架上           |
| refactoring                           | 重构               | 不改变外部行为的前提下改善内部结构             |
| user requirement specification（URS） | 用户需求规格说明书 | 汇总用户需求的正式交付文档                     |
