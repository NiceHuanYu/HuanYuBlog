## 0 用例画完之后，重复出现了

第一版用例图通常是这样的：每个用例各画各的，画完一看，「校验库存」这件事在「下单」「取消订单」「改签」里各写了一遍。

用例模型的精炼（refining the use case model）要解决的就是这类重复，以及**把可选流程从主流程里拆出来**。有三种关系可以用。

![精炼用例模型的三种方式：include 把公共步骤抽成被复用的用例，extend 描述可选或例外流程，泛化把共同部分抽象成父级，包括参与者泛化与用例泛化](/images/sw-design-notes-10-include-extend.svg)

## 1 include：把公共步骤抽出来

**include 关系（include relationship）**表示：这个用例**每次执行时都会**用到另一个用例。

```
下单      --include--> 校验库存
取消订单  --include--> 校验库存
改签      --include--> 校验库存
```

### 1.1 它会每次都执行吗

判断标准就一条：**这个步骤会不会每次都被执行？**

「校验库存」每次下单都要做，所以适合 include。而被 include 的那个用例（图上叫 `校验库存`）通常不是一个完整的目标，它更像是被复用的一个片段 —— 这是 include 的一个特征：**被 include 的用例一般不独立出现。**

## 2 extend：可选与例外

**extend 关系（extend relationship）**表示：在特定条件下，主用例会**额外**做一件事。

```
下单   <--extend--   使用优惠券
下单   <--extend--   超时未支付自动取消
```

判断标准：**这个步骤只在某些条件下发生，而主用例本身并不知道它存在。**

最后半句是关键。主用例（base use case）不需要知道有优惠券这回事 —— 「下单」该做的就是下单。优惠券是叠加上去的可选项。**如果主用例必须知道对方的存在才能跑通，那就不是 extend，而是 include 或者主流程的一部分。**

### 2.1 扩展点挂在哪里

这里有个衍生出来的「扩展点（extension point）」概念：扩展用例挂在主用例的哪个位置触发。比如「使用优惠券」的扩展点是「进入支付之前」。

## 3 include 和 extend 的区别，一句话

| | include | extend |
| --- | --- | --- |
| 执行时机 | **每次都会执行** | 只在特定条件下执行 |
| 依赖方向 | 主用例依赖被包含用例 | 扩展用例依赖主用例 |
| 主用例是否知道 | 知道，是它的必经步骤 | 不知道，是可叠加的行为 |
| 典型用途 | 复用公共步骤 | 可选功能、例外流程 |

记不住的时候，问一句：**「这一步能不做吗？」** 不能不做 → include；可能不做 → extend。

## 4 泛化：把共同的部分提到父级

**泛化（generalization）**是把多个元素共同的部分抽象成一个父级。用例模型里有两个地方能用到：

### 4.1 参与者泛化

**① 参与者泛化（generalization of actors）。** 例如「常旅客」和「企业客户」都是「旅客」，都要能查询和预订，区别只在少数几件事上。把共同的部分放到父级「旅客」，子级只描述差异。

### 4.2 用例泛化

**② 用例泛化（generalization of use cases）。** 例如「电话预订」和「网上预订」都是「预订」，流程主体相同、渠道细节不同。把「预订」作为父用例（抽象用例，abstract use case，本身不直接执行），子用例继承并覆盖差异部分。

### 4.3 收益与代价

泛化的价值在于**改动集中**：共同流程变一次，所有子级都跟着变。代价是抽象层次变多，读图的人要多跳一层。所以只有当「差异确实很小、共同部分确实很多」时才值得用。

## 5 精炼到什么程度就该停

精炼有一个明显的收益递减点。把每个用例都拆成 include、再给每个角色都建一个父级，最后得到一张谁也看不懂的图 —— 这就是过度抽象（over-abstraction）。

一条经验判断：**如果精炼之后，业务方看图的难度上升了，那这次精炼就是不值得的。**用例模型的首要读者是业务方，不是建模的人。

另外，用例变多之后的分组（use case package）是另一层组织手段，笔记 08 已经讲过。

## 6 先细化哪一个：两种替代方案

最后剩一个实际问题：用例很多，先细化哪个？两种常见策略：

### 6.1 策略一：先做主线

**策略一：先做主线。** 先把核心流程（下单、支付）细化到能开发，再处理分支。适合要尽早看到可用版本的场景。

### 6.2 策略二：先做分支

**策略二：先做分支。** 先把例外流程（超时、失败、退款）理清。适合业务规则复杂、例外很多、返工成本高的场景。

### 6.3 怎么选

选哪种取决于**哪一类问题更容易推翻已有的设计**。如果例外流程经常改主线，那就该先做分支 —— 因为先做的主线很可能白做。

## 7 本节自测

1. 判断用 include 还是 extend，只需要问哪一个问题？
2. 「下单」需要知道「使用优惠券」的存在吗？这个问题的答案说明了什么？
3. 参与者泛化和用例泛化分别在什么情况下有用？
4. 精炼到什么程度就该停下？判断依据是什么？
5. 什么情况下应该先细化例外流程，而不是主线？

## 8 术语表

| 术语 | 中文 | 一句话解释 |
| --- | --- | --- |
| include relationship | 包含关系 | 主用例每次执行都会用到的公共步骤 |
| extend relationship | 扩展关系 | 只在特定条件下叠加到主用例上的行为 |
| base use case | 基础用例 | 被扩展的那个主用例 |
| extension point | 扩展点 | 扩展用例挂载到主用例上的触发位置 |
| generalization of actors | 参与者泛化 | 把多个角色的共同部分抽象成父角色 |
| generalization of use cases | 用例泛化 | 把多个用例的共同流程抽象成父用例 |
| abstract use case | 抽象用例 | 只用于被继承、本身不直接执行的用例 |
| refining the use case model | 精炼用例模型 | 用 include、extend、泛化整理用例结构 |
| use case package | 用例包 | 按主题、角色或阶段对用例分组 |
| over-abstraction | 过度抽象 | 抽象层次过多，反而降低可读性 |
