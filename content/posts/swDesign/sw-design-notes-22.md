> 这是我在学习软件分析与设计时整理的系列笔记。概念部分是我按自己的理解写的，示例与图示都是自己编、自己画的。理解有偏差的地方欢迎指出。

## 0 跳过分析直接写代码会怎样

需求给了、数据库也建好了，直接开始写代码 —— 这是很多项目的实际做法。它通常在三到六个月后付出代价：

- 界面上的一段逻辑，被复制到三个页面里（因为写的时候没想清楚该放哪）；
- 业务规则散落在控制器、数据访问和界面代码里；
- 想做一个「批量导入」，发现没有地方可以复用已有的处理逻辑。

**分析建模（analysis modelling）** 就是在需求和代码之间插一层：**先想清楚每个用例由哪些对象协作完成。**

## 1 它在流程里的位置

| 阶段 | 回答的问题 | 产物 |
| --- | --- | --- |
| 需求建模（requirements modelling） | 系统要做什么 | 用例模型、活动图 |
| 分析建模（analysis modelling） | 由哪些对象协作完成 | 分析模型（类图 + 顺序图） |
| 设计建模（design modelling） | 怎么落到平台与数据上 | 设计模型（含表、访问层） |

分析建模有个重要特征：**它刻意不关心实现平台。**不讨论用哪个框架、哪张表、什么字段类型 —— 只讨论职责怎么分。**先把「该谁做」定下来，再决定「怎么做」。**

## 2 三种分析对象

分析对象（analysis object）通常按职责分成三种**构造型（stereotype）**：

### 2.1 边界对象

**① 边界对象（boundary object）** —— 系统与外部交互的地方：界面、外部接口。它负责接收输入与展示结果，**不负责业务规则**。

它的一个重要特征是**改动最频繁**：界面几乎每次迭代都在变。所以业务规则一定不能写在边界对象里，否则每次改界面都要重新验证业务逻辑。

### 2.2 实体对象

**② 实体对象（entity object）** —— 业务上需要长期记住的东西，也就是笔记 09 里的业务实体。它承载数据与规则，通常能对应到数据表。

### 2.3 控制对象

**③ 控制对象（control object）** —— 协调一个用例的执行顺序：接收请求，判断该交给谁处理（这个动作就是委派，delegation），再汇总结果。它本身不该堆积业务规则。

控制对象是三者里最容易失控的 —— 因为它「什么都管」，很容易变成什么都往里塞的**上帝类（god class）**。一个判断方法：**如果这个类的方法里出现了大量「先查 A、再判断 B、然后更新 C」，那这些逻辑大多属于实体对象。**

## 3 用顺序图做一次用例实现

### 3.1 做法

把「每个用例由哪些对象协作完成」画出来，这个过程叫**用例实现（use case realization）**。

做法是：取一个用例的**主流程（basic flow）**，逐个步骤问「这一步由谁执行」，把参与者与对象的交互画成顺序图。

### 3.2 一个简化例子

举个简化例子（查询车辆）：

1. 界面收到「查询车牌」的输入 → 调用业务对象的查询方法；
2. 业务对象需要数据 → 调用数据对象的按车牌查询；
3. 数据对象返回结果 → 业务对象返回给界面。

这张图里出现的每个对象，就是三种分析对象各一个：**界面是边界对象，车辆是实体对象，数据访问是另一种边界对象**。

## 4 从顺序图导出类

### 4.1 导出规则

顺序图画清楚之后，类图基本就出来了 —— 导出规则是机械的：

| 顺序图里的东西 | 对应到类图 |
| --- | --- |
| 每个参与对象 | 一个类 |
| 对象收到的消息 | 该类的一个操作 |
| 需要记住的数据 | 类的属性 |
| 谁调用谁 | 类之间的关系 |

### 4.2 为什么先画顺序图

这也是为什么推荐**先画顺序图、再画类图**：如果反过来，先列一堆类再想它们怎么协作，很容易列出一批「看起来合理但用不上」的类。

## 5 关系上的限制

### 5.1 不是所有关系都能随便用

从顺序图导出关系时，有一点要留意：**不是所有关系都可以随便用。**

- **依赖** —— 出现在方法参数里，最轻；
- **关联** —— 需要长期保留引用时才用；
- **聚合 / 组合** —— 要有明确的整体—部分语义。

一个常见错误是「为了让图好看，把所有关系都画成组合」。判断依据还是那句：**整体没了，这个部分还活得下去吗？**

### 5.2 关系方向要反映调用方向

还有一条实践建议：**关系的方向要能反映调用方向。**如果 A 调 B、B 又调 A，那张图上会出现环 —— 环通常不是错，但值得停下来看看是不是职责切分有问题。

## 6 类图怎么文档化（documenting the class diagram）

分析模型最终要交出去，类图的说明通常有三种组织方式：

1. **每张图配一段文字** —— 逐个类说明职责。适合类少的场景；
2. **统一一张职责表** —— 类名 + 职责 + 关键操作 + 协作对象。适合类多的场景，也便于对照检查职责有没有重叠；
3. **在图上直接标注** —— 把职责写在类旁边的注释框里。适合评审时快速对齐。

三种方式可以混用。关键是**每个类的职责必须有一句话能说清楚** —— 说不清，通常意味着这个类做了两件不相关的事。

## 8 术语表

| 术语 | 中文 | 一句话解释 |
| --- | --- | --- |
| analysis modelling | 分析建模 | 确定每个用例由哪些对象协作完成 |
| analysis object | 分析对象 | 分析模型里承担一种职责的对象 |
| stereotype | 构造型 | 给模型元素附加语义的分类标记 |
| boundary object | 边界对象 | 系统与外部交互的对象，如界面与外部接口 |
| entity object | 实体对象 | 承载业务数据与规则的对象 |
| control object | 控制对象 | 协调用例执行顺序的对象 |
| use case realization | 用例实现 | 用对象协作把用例的流程具体化 |
| basic flow | 主流程 | 一切顺利时的步骤序列 |
| delegation | 委派 | 把请求转给该处理它的对象 |
| god class | 上帝类 | 职责过多、什么都管的类 |
| documenting the class diagram | 类图文档化 | 用文字、表格或注释说明每个类的职责 |
