> 这是我在学习软件分析与设计时整理的系列笔记。概念部分是我按自己的理解写的，示例与图示都是自己编、自己画的。理解有偏差的地方欢迎指出。

## 0 当访谈结论和数字对不上

自建的例子：某在线零售团队访谈了十几位用户，其中大多数人表示「价格是我最看重的因素」。听起来很清楚，价格就是第一优先级。

但三个月的订单数据说了另一件事：价格最低的那批商品转化率很一般，真正卖得好的是贵 15%–20%、但配送时段更灵活的那批。

这不是谁在说谎。**「我认为我重视价格」和「我在具体情境下愿意为便利付钱」可以同时成立。**访谈拿到的是自我认知，数据拿到的是实际取舍。

笔记 02 已经讲过：数据告诉你发生了什么，用户告诉你为什么。这一篇讲数据这一侧具体怎么用。

## 1 分析的四个层次

![分析的四个层次与业务目标的映射：四个层次从低到高是 descriptive 发生了什么、diagnostic 为什么发生、predictive 可能会发生什么、prescriptive 应该怎么做；下方给出三行业务目标到分析层次与所需数据的映射示例](/images/sw-design-notes-06-analytics-layers.svg)

### 1.1 四个层次与它们的前提

从低到高，分析（analytics）通常分四层：

| 层次 | 回答的问题 | 需要的前提 | 典型手段 |
| --- | --- | --- | --- |
| descriptive analytics | 发生了什么 | 数据能采到、口径统一 | 报表、漏斗、分布统计 |
| diagnostic analytics | 为什么发生 | 有可对比的维度或分组 | 分群对比、相关性分析 |
| predictive analytics | 可能会发生什么 | 历史规律稳定、样本足够 | 回归、时间序列、分类模型 |
| prescriptive analytics | 应该怎么做 | 各选项的成本可比较 | 优化模型、决策规则 |

关键在第三列：**每一层都比上一层多一个前提。**很多数据项目失败，不是因为模型不够好，而是基础没打牢就直接去做上一层 —— 比如口径都没统一，就急着建预测模型。

### 1.2 处理文本的两类方法

除了这四层，还有一类方法处理的是非结构化的文本，而不是报表数字：sentiment mining（情感挖掘）从评价、客服记录里提取情绪倾向；big data analytics（大数据分析）面对的是数据量本身超出常规工具处理能力的场景。它们的共同点是：先解决「怎么把文本变成可统计的东西」，再谈分析。

## 2 数据准备、搜集与应用地图

### 2.1 三步，写成一张表

数据侧的工作可以归成三步：

1. **明确业务目标（business objective）** —— 这件事是为了改什么？通常要落成可测量的 KPI（关键指标）。
2. **选分析手段** —— 对应上面四个层次里的哪一层。
3. **列出所需数据** —— 需要哪些字段、从哪个系统来、能不能采到。

把这三步写成一张表，就是**应用地图（application map）**：每一行从「目标」推到「手段」再推到「数据」。它同时暴露两种问题：目标说不清的，以及数据拿不到的。

### 2.2 两个需要单独留意的动作

这张表里有两个动作需要单独留意：

- **data preparation（数据准备）** —— 清洗、补全、统一口径。这一步通常占掉整个数据工作一半以上的时间；
- **data collection（数据搜集）** —— 有些数据现在根本没采，需要在系统里新增埋点。而新增埋点意味着这是**需求**，要写进需求文档。

第二点是数据侧最容易漏掉的产出：**「我们需要采集这些字段」本身就是一条需求。**

## 3 数据能做什么、不能做什么

### 3.1 能做：量化、验证、发现异常

**能做：**

- 量化规模 —— 到底是 5% 的人这么做，还是 80%；
- 验证假设 —— 笔记 04 里那些「假设与理由」，靠数据推翻或确认；
- 发现异常 —— 找出与预期不符的地方，提示这里有没被理解的东西。

### 3.2 不能做：解释原因

**不能做：**

- **解释原因。** 数据能告诉你取消率在下单页飙升，但不会告诉你是因为运费没提前说明。

所以回到那个词：data-informed design。数据负责指出「哪里不对劲」，用户负责解释「为什么」。

## 4 数据最容易在哪几个地方骗你

- **样本偏差（sample bias）。** 只统计了用了这个功能的人，没用过的人不在样本里，而后者往往才是重点。
- **幸存者偏差（survivorship bias）。** 你看到的是留下来的用户，流失用户的行为轨迹在他们离开后就断了。
- **指标口径不一致（metric definition）。** 「活跃用户」在两张报表里定义不同，结论就会互相打架。
- **数据质量（data quality）问题。** 埋点漏报、字段缺失、时间戳时区错乱 —— 这类问题比想象中常见，且会静默地污染所有结论。
- **数据管道（data pipeline）中断。** 中间某个环节停了几天，导致对比的两个时间段根本不可比。

这五条有个共同特征：**它们都不会报错，只会给出看起来正常的错结论。**所以在用数据下判断前，先花点时间确认数据本身可信。

## 5 数据侧的四个准备动作

把上面这些收成可执行的四步：

1. **先写业务目标与 KPI**，再谈数据。目标不明确的报表，做出来也没人看；
2. **确定基线（baseline）** —— 改动之前的数值是多少？没有基线就无法判断改进有没有效果；
3. **检查数据质量** —— 这个时间段的数据是全的，还是埋点刚上线了一半；
4. **最后才看数**，并且把结论写成可验证的假设，回到数据里确认（和笔记 02 的四步法同一个落点）。

## 6 本节自测

1. 访谈里大多数人说自己最看重价格，但订单数据显示不是，这个矛盾怎么解释？
2. 分析的四个层次里，为什么不能跳过前两层直接做预测？
3. 什么是应用地图（application map）？它能暴露哪两类问题？
4. 为什么「新增埋点」本身也是一条需求？
5. 举出一个「不会报错、但会给出错结论」的数据问题。

## 7 术语表

| 术语 | 中文 | 一句话解释 |
| --- | --- | --- |
| analytics | 分析 | 从数据中提取结论的方法总称 |
| descriptive analytics | 描述性分析 | 回答发生了什么 |
| diagnostic analytics | 诊断性分析 | 回答为什么发生 |
| predictive analytics | 预测性分析 | 回答可能会发生什么 |
| prescriptive analytics | 处方性分析 | 回答应该怎么做 |
| business objective | 业务目标 | 做这件事要达成的业务结果 |
| KPI | 关键绩效指标 | 用来衡量目标是否达成的可量化指标 |
| application map | 应用地图 | 把业务目标、分析手段与所需数据对应起来的表 |
| data preparation | 数据准备 | 清洗、补全、统一口径等前置工作 |
| data collection | 数据搜集 | 采集原始数据的过程，常需要新增埋点 |
| data quality | 数据质量 | 数据在完整性、准确性、一致性上的可靠程度 |
| data pipeline | 数据管道 | 数据从产生端流到使用端所经过的环节 |
| metric definition | 指标口径 | 一个指标具体怎么算的定义 |
| sample bias | 样本偏差 | 样本不能代表整体而产生的偏差 |
| survivorship bias | 幸存者偏差 | 只看到留存下来的对象，忽略已消失的 |
| baseline | 基线 | 改动之前的数值，用于对比改进效果 |
| sentiment mining | 情感挖掘 | 从文本中提取情绪倾向的分析方法 |
| big data analytics | 大数据分析 | 面向超大规模数据的分析手段 |
