> 这是我在学习软件分析与设计时整理的系列笔记。概念部分是我按自己的理解写的，示例与图示都是自己编、自己画的，参考的是 UML 规范这类公开资料。理解有偏差的地方欢迎指出。

## 0 为什么需要一种共同的画法

一个五人团队，如果每个人用自己的方式表达「客户有多张订单」，就会出现五种画法：有的画箭头、有的写文字、有的直接画表格。讨论的力气全花在「你画的这个箭头什么意思」上。

**UML（Unified Modeling Language）** 的价值就在这里：**它是一套约定的符号**，让「这张图在说什么」不再需要额外解释。

注意关键词是「符号」。UML 不规定你怎么做设计，只规定你怎么把设计画出来。

## 1 UML 在流程里的位置

### 1.1 各工作流常用哪些图

UML 的各类图并不是都用在同一个阶段，它们对应不同的工作流：

| 工作流 | 常用的图 |
| --- | --- |
| 业务建模（business modeling） | 用例图（use case diagram）、活动图 |
| 需求（requirements） | 用例图、活动图 |
| 分析（analysis） | 类图（class diagram）、顺序图 |
| 设计（design） | 类图、顺序图 |
| 实现（construction / implementation） | 类图（贴近代码的细化） |
| 测试（testing） | 用例图、顺序图（推导测试场景） |

### 1.2 同一张图会反复出现

看这张表能发现一件事：**同一个类型的图会反复出现，只是细节程度不同。**分析阶段画「客户」这个概念，设计阶段可能画到「客户表对应的实体类」。所以不要把「这张类图到底算分析还是设计」当成是非题。

## 2 类图：三格结构与可见性

![UML 类符号的三格结构与关系到 Java 的映射：类符号从上到下是类名、属性、操作，可见性用加号减号井号表示；右侧列出关联、聚合、组合、继承、依赖五种关系在 Java 里对应的写法，底部说明顺序图的三要素](/images/sw-design-notes-21-uml-mapping.svg)

### 2.1 类符号的三格

类图（class diagram）里最基本的元素是类符号（class symbol），它由三格组成：

1. **类名**；
2. **属性列表（attribute list）** —— 对象需要记住的状态；
3. **操作（operation）** —— 对象能提供的行为。

### 2.2 可见性在传达什么

属性前面可以标**可见性（visibility）**：`-` 表示 private（只有自己可见）、`+` 表示 public（所有类可见）、`#` 表示 protected（子类可见）。

这个符号看着是细节，但它其实在传达设计意图：**一个字段被标成 `+`，等于宣布「任何人都能改它」** —— 这在多数情况下都不是想要的结果（见笔记 20 关于封装的讨论）。

## 3 五种关系

### 3.1 符号与含义

| 关系 | UML 符号 | 含义 |
| --- | --- | --- |
| dependency | 虚线箭头 | 临时使用 |
| association | 实线（可带重数 multiplicity） | 长期持有引用 |
| aggregation | 空心菱形 | 部分可独立存在 |
| composition | 实心菱形 | 部分随整体消亡 |
| inheritance | 空心三角，指向父类 | is-a |

### 3.2 每种关系落到 Java 的写法

关键是**每种关系落到代码里都不一样**：

| 关系 | Java 里的典型写法 |
| --- | --- |
| Association | 字段持有集合，例如 `List<Order> orders` |
| Aggregation | 集合字段，但元素由外部传入（构造参数或设置方法） |
| Composition | 集合字段，元素在整体内部创建与管理，不对外暴露 |
| Inheritance | `class VipCustomer extends Customer` |
| Dependency | 出现在方法参数或局部变量里，不保留引用 |

### 3.3 符号不是装饰

**这些符号不是装饰。**把组合画成聚合，不只是图错了 —— 它会直接误导实现的人该怎么管理对象的生命周期。

## 4 顺序图：三要素

### 4.1 三个基本元素

**顺序图（sequence diagram）** 描述对象之间的交互，纵向表示时间。三个基本元素：

- **生命线（lifeline）** —— 参与这次交互的每个对象，用竖直虚线表示；
- **消息（message）** —— 对象之间的调用，用横向箭头表示，箭头方向就是调用方向；
- **激活条（activation）** —— 表示某段时间这个对象正在处理（收到消息到返回结果之间）。

### 4.2 它还能暴露职责错位

顺序图有一个容易被忽略的优点：**它能暴露「谁该知道谁」这个问题。**如果一张顺序图里，界面对象直接调用了数据对象、又自己做了业务判断，那这张图本身就在提示职责分错了位置 —— 这正是笔记 22 要展开的内容。

## 5 对象图（object diagram）

类图描述「有哪些类」，**对象图（object diagram）** 描述「某一时刻具体有哪些对象、它们的引用关系如何」，例如 `订单A1091`、`张三（客户）`。

它用得比类图少，但在排查问题时很有用：**当你怀疑「这两个对象之间到底有没有关联」时，画一个对象图比读代码快。**

## 6 关于工具

建模工具（modeling tool）很多，从在线工具到桌面工具都有。选的时候只需要看两点：

- **能不能正确表达 UML 符号**（尤其是四种菱形与三角）；
- **改起来方不方便** —— 需求阶段改图是常态，工具如果改一次要重画，你就会开始少改。

工具本身不影响设计质量：**用工具画得整齐，不等于关系画对了。**

## 7 本节自测

1. UML 规范规定了什么、又没有规定什么？
2. 同一个类名在分析阶段和设计阶段，画的详细程度为什么不同？
3. 聚合和组合在 Java 里的写法差别体现在哪？
4. 顺序图的三个基本元素分别是什么？纵向代表什么？
5. 什么情况下画对象图比读代码更有效？

## 8 术语表

| 术语 | 中文 | 一句话解释 |
| --- | --- | --- |
| UML | 统一建模语言 | 一套约定的建模符号 |
| class diagram | 类图 | 描述类、属性、操作与关系的静态结构图 |
| object diagram | 对象图 | 描述某一时刻具体对象及其引用关系 |
| sequence diagram | 顺序图 | 用消息往来描述交互，纵向表示时间 |
| use case diagram | 用例图 | 描述参与者、用例与系统边界 |
| class symbol | 类符号 | 类图里表示一个类的矩形，通常分三格 |
| attribute list | 属性列表 | 类符号中间那一格，列出对象的状态 |
| operation | 操作 | 类符号下面那一格，列出对象的行为 |
| visibility | 可见性 | 用 +、-、# 表示成员的开放程度 |
| dependency | 依赖 | 临时使用另一个对象的关系 |
| association | 关联 | 长期持有对方引用的关系 |
| multiplicity | 重数 | 一端可以对应多少个实例 |
| aggregation | 聚合 | 部分可独立存在的整体—部分关系 |
| composition | 组合 | 部分随整体消亡的强聚合 |
| inheritance | 继承 | 子类复用并覆盖父类定义的关系 |
| lifeline | 生命线 | 顺序图里表示一个参与对象的竖线 |
| message | 消息 | 对象之间的一次调用 |
| activation | 激活条 | 表示对象正在处理的时间段 |
| modeling tool | 建模工具 | 用来绘制 UML 图的软件 |
