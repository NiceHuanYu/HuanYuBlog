## 0 从一段关键词分类的代码说起

要给客服邮件自动分类，最传统的写法是这样：

```python
BILLING = ["invoice", "payment", "refund", "billing"]
TECHNICAL = ["error", "bug", "issue", "not working", "crash"]

def classify(text):
    t = text.lower()
    if any(k in t for k in BILLING):
        return "billing"
    if any(k in t for k in TECHNICAL):
        return "technical"
    return "general"
```

这段代码的问题不在于写得不好，而在于**规则是人预先想出来的**。用户换个说法（「我这个月的钱怎么又扣了」），规则就失效了 —— 除非你再去补关键词。

换一种做法：把分类这件事交给一个能理解语义的模型，让它自己判断，甚至让它自己决定「要不要再去查一下订单数据才能回答」。这就是 AI agent（智能体）的起点。

## 1 AI agent 是什么

![AI Agent 的五项能力、四个核心组件与两种实现路径：能力是推理、行动、观察、规划、自主与协作；组件是推理核心、记忆、工具、指令与编排；实现路径分小目标加固定流程与高层目标加动态决策两类](/images/sw-design-notes-11-agentic-ai.svg)

### 1.1 五项能力

一个 agentic AI（智能体式 AI）系统，通常具备五项能力：

| 能力 | 含义 |
| --- | --- |
| reasoning（推理） | 从已知信息得出结论、做判断 |
| acting（行动） | 真的去做事：发邮件、改数据、建报表 |
| observing（观察） | 感知环境：读文件、看返回结果、检查状态 |
| planning（规划） | 把大目标拆成任务和子任务 |
| autonomy（自主）与协作 | 不等指令就能推进；也能与人或其他 agent 协作 |

### 1.2 分水岭：planning 与 autonomy

这五项里，**planning 和 autonomy 才是分水岭**。只会调一次模型、拿一次结果的东西不叫 agent；能自己拆解、自己决定下一步、遇到情况自己调整的才叫。

## 2 四个核心组件

| 组件 | 作用 |
| --- | --- |
| Brain（reasoning core，推理核心） | 处理输入、拆解目标、规划动作、判断何时结束 |
| Memory（记忆） | 短期记忆（short-term memory）保存当前会话上下文；长期记忆（long-term memory）用向量数据库（vector database）或知识图谱（knowledge graph）保存历史与知识，通常以 RAG（检索增强生成）方式使用 |
| Tools（工具） | 可调用的外部能力：API、数据库查询、网页浏览 |
| Instructions（指令）与 orchestration（编排） | 指令是定义 agent 角色、边界与行为的 prompt；编排负责串起单 agent 的步骤，或协调多 agent（multi-agent）之间的分工。实际落地时，这套东西通常被打包成一个 framework（框架）。 |

### 2.1 长期记忆保存的是什么

关于长期记忆要多说一句：**它保存的不是「对话记录」，而是可检索的知识。**这也是为什么它需要向量数据库 —— 因为检索靠的是语义相似，而不是精确匹配。

## 3 选型：batch、程序，还是 agent

### 3.1 三种方案的分工

不是所有事都该交给 agent。三种方案各有各的位置：

| | batch job（定时批处理） | 程序化（RPA / scripting） | agentic AI |
| --- | --- | --- | --- |
| 自主程度 | 无，按计划跑 | 低，固定规则 + 人工介入 | 高，自主决策 |
| 逻辑性质 | 静态 | deterministic（确定性） | 自适应、non-deterministic（非确定性） |
| 任务性质 | 重复 | 重复 | cognitive（认知型） |
| 实现方式 | 编码 | 编码 / 点选录制 | 写规格说明 |
| 典型场景 | 月底报表 | 购物车结算、开票 | 客服、研究助理 |

### 3.2 一句话选型标准

选型的一句话标准：**这一步的判断，是「照规则办」还是「要看情况」？**照规则办就用程序，几乎不给模型发挥空间；要看情况才轮到 agent —— 而且要看情况的频率越高、越难穷举，agent 的价值才越大。

## 4 两种实现路径

同样是「用 agent 做客服」，实现方式可以差很远。

### 4.1 路径一：小目标 + 固定流程

把任务拆成明确步骤，每一步走哪条分支由人预先定好：

```
先分类邮件 → 按分类取数据 → 生成回复 → 记日志
```

这里面虽然调用了模型，但控制流是人写的。行为可预测、容易测试、容易追踪。

### 4.2 路径二：高层目标 + 动态决策

只告诉 agent 目标（「解决这位客户的问题」）和可用工具（查账单、查知识库、转人工），**由 agent 自己决定调哪个工具、调几次、什么时候停**。

路径二能处理没预先想到的情况，代价是行为不可预测：同一个输入，两次运行可能走不同的路。**这也是为什么它必须配护栏（guardrail）和人工介入点（human-in-the-loop）。**

## 5 搭建方式：按流程，还是按角色

现在的 agent 搭建工具（agent builder）通常提供两种组织方式，很多还是 no-code（免代码）形态：

- **按流程（by workflow）** —— 在画布上拖节点，用条件分支串起来。适合路径一；
- **按角色（by roles）** —— 定义几个角色（数据搜集员、文献分析员、报告撰写者），让它们协作完成任务。适合路径二里的多 agent 分工。

按角色的方式看起来很吸引人 —— 描述一下目标，几个 agent 就自己把研究报告写出来了。但要记住：**角色越多，失败模式越多**，见下一节。

## 6 四类必须提前防住的失败

这一类系统的失败模式和传统软件完全不同，值得单独列出来：

### 6.1 提示注入（prompt injection）

攻击者把指令藏进 agent 会读到的内容里。三种常见形式：

- prompt-based：直接在对话里说「忽略之前的指令，做某某事」；
- web-based：在提交的表单里夹带指令；
- context-based：把指令藏在 agent 通过 RAG 读到的文档、邮件里。

### 6.2 越狱与多 agent 串谋

例如用一个模型自动迭代生成攻击提示、另一个模型负责评测；或者让恶意指令进入某个 agent 的记忆，**自动传染给其他 agent**（infectious jailbreak）。

### 6.3 记忆投毒（memory poisoning）

一个 agent 把幻觉写进共享记忆，其他 agent 当成事实用下去，错误就这样扩散。

### 6.4 基础风险与工程对策

安全与隐私（agent 常常要接触敏感数据）、偏见与公平性、可解释性不足（所以 explainable AI 很重要）、行为不可预测、以及落地时的组织阻力。

工程上的对策包括：把 agent 的权限压到最小、对工具调用做白名单、给关键动作加人工确认（human-in-the-loop）、留下完整的执行记录（traceability）、以及为每一步准备失败回退（fallback logic）。

## 7 设计方法本身的演进

### 7.1 六个阶段的演进

有意思的是，设计这类系统的方法论也在演进：

| 阶段 | 做法 | 控制方式 |
| --- | --- | --- |
| user-driven | 从用户需求出发 | 人 |
| data-driven | 从数据出发 | 人 |
| prompt-based | 写提示词让模型干活 | 人 |
| spec-driven（规格驱动） | 把大目标拆成小目标，逐步喂给 agent | 子目标 + 定期人工审查 |
| role-based design（角色驱动） | 用角色和约束引导 agent | 约束与护栏 |
| harness-driven（框架驱动） | 用 agent OS / agentic harness 管理完整的规划—行动—评估循环 | 系统化编排 |

「harness」指的是那层软件包装：它管住 agent 的生命周期，让它按周期运转，而不是单次提问；同时负责持续验证、自动化测试、记忆管理与专用工具。

### 7.2 一条规律：自主性越高，控制越厚

看下来会发现一个规律：**自主性每提高一级，控制手段也必须跟着加一层。**这不是倒退，而是这类系统能被信任的前提。

## 8 Artifact-First：从产出倒推

### 8.1 三个要回答的问题

在决定用不用 agent 之前，有个更简化的框架值得先用一遍 —— **Artifact-First（产出优先）**：

1. **Artifact（产出）** —— 最终要交出什么？这件事替代了谁的什么工作？谁用、用什么格式？
2. **Context（上下文）** —— 需要哪些数据与文档？来自内部（RAG）还是外部（网页）？需要多新鲜？
3. **Workflow（工作流）** —— 目标与子目标是什么？护栏、约束、人工审查点放在哪？由哪个 agent、什么时候运行？

### 8.2 操作顺序

它的操作顺序是：先找出业务里那些**重复出现又有价值**的产出，挑一个高杠杆的，定义清楚它为什么有用（给谁看、输入什么、什么格式），然后搭一条最小的流程把上下文变成这个产出 —— 最后才考虑要不要升级成 agent。

触发方式（trigger）可以是时间、某个事件，或者手动。

这么做的理由很实际：**从产出倒推，能避免为了用 agent 而用 agent。**

## 9 这对需求分析意味着什么

### 9.1 需求文档里多了五类内容

回到这个系列的主线。这类系统进入项目之后，需求文档里多了几类以前没有的内容：

- **agent 的边界** —— 它能做哪些动作、不能做哪些动作；
- **护栏与约束** —— 哪些条件必须停下来问人；
- **人工介入点** —— 哪些步骤必须有人确认，谁是那个人；
- **失败回退** —— 出问题时回到哪一步、由谁接手；
- **可观测性要求** —— 需要留下哪些记录，以便事后解释「它为什么这么做」。

这几条本质上还是需求工作 —— 只是描述的对象从「系统该做什么」变成了「系统可以自主到什么程度」。这也是为什么笔记 15 要专门讲非功能需求：**这类系统对安全、可靠、可解释的要求，比传统系统更高。**
