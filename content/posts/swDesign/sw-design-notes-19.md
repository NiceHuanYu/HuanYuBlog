## 0 一次改地址引发的麻烦

某客户搬了家。运营在系统里改了客户档案上的地址。

三天后发现：他上个月的两张订单，发票上寄的还是旧地址。订单表里也存了一份客户地址 —— 当时为了「查起来方便」，一份地址被存了三处，改的时候只改了一处。

这不是粗心，而是**数据冗余（data redundancy）** 必然会带来的**更新异常（update anomaly）**：**同一份事实存在多处，就一定会有忘记同步的那一天。**

规范化（normalization）要解决的就是这件事。

## 1 三种异常

冗余带来的问题一共三类：

| 异常 | 表现 |
| --- | --- |
| 更新异常（update anomaly） | 改一处漏一处，数据自相矛盾 |
| 插入异常（insert anomaly） | 想录入某条信息，却因为没有别的主数据而录不进去 |
| 删除异常（delete anomaly） | 删掉一条记录，顺带把别的信息也弄丢了 |

插入异常的典型例子：如果订单和客户信息存在同一张表里，那么一个还没下过单的新客户，就没有地方录入。**「想存 A，但必须先有 B」这种别扭，就是插入异常的信号。**

## 2 UNF 到 3NF：每一步拿走一种重复

规范化的做法是**对表逐条套用规则**，每套用一次就上一个范式。

### 2.1 未规范化形式（unnormalized form, UNF）

原始的宽表：一张表里既有订单信息，又有客户信息，还有多行商品明细挤在同一格里。

### 2.2 第一范式（first normal form, 1NF）

消除**多值属性（multivalue attribute）** 与**重复组（repeating group）**：

- 每个单元格只放一个值（原子值，atomic value）；
- 把重复出现的商品行拆成独立记录，而不是塞在一格里。

1NF 之后，重复的问题只是被摊开了，还没有解决。

### 2.3 第二范式（second normal form, 2NF）

消除**部分依赖（partial dependency）**：

- 前提是这个表有复合主键；
- 规则是：**非主键字段必须依赖整个主键**，不能只依赖其中一部分。

举例：订单明细表的主键是「订单号 + 项号」。商品名称只依赖「项号」，不依赖「订单号」—— 这就是部分依赖，应该把商品信息移到商品表。

### 2.4 第三范式（third normal form, 3NF）

消除**传递依赖（transitive dependency）**：

- 规则是：**非主键字段不能依赖另一个非主键字段**；
- 典型例子：订单表里有「客户号」和「客户地址」。地址依赖的是客户号（一个非主键字段），而不是订单号 —— 所以地址该搬到客户表。

### 2.5 函数依赖：三条规则的统一说法

函数依赖（functional dependency）是这三条规则背后的统一说法：**如果知道 A 就能唯一确定 B，就写成 A → B。**规范化要做的，是让所有非主键字段都直接依赖于主键。

## 3 派生字段（derived attribute）不存

订单明细里有「单价」和「数量」，那么「小计」要不要存？

**不要。** 因为小计可以由另外两个字段算出来 —— 这类字段叫**派生字段（derived attribute）**。存它的代价是：每次单价或数量变化，你都必须记得同步更新小计；漏一次，数据永久不一致。

正确做法是**在需要的地方算**（查询时计算、或由视图/应用层计算）。如果确实因为性能原因要存，那要配套约定清楚「谁负责更新、什么时候更新」。

这条规则和笔记 09 讲业务实体时说的「能算出来的不要存」是同一条。

## 4 优化：把表合回去的两种情形

规范化不是终点。有些场景下，把表适度合回去反而更好 —— 这叫**优化（optimization）**，它和规范化是**方向相反的两种权衡**。

常见的两种情形：

1. **频繁关联查询的小表。** 两张表总是一起查、且都很少变动，合并可以减少连接；
2. **只在一处使用的数据。** 某个字段只在同一个业务流程里被读写，且没有独立生命周期。

关键是把话说清楚：**这不是「没做规范化」，而是权衡后退一步。**判断依据仍然是那条：这份数据会不会因为存在两处而不一致？如果合起来不会引入冗余，那合起来就是合理的。

## 5 逻辑数据模型（LDM）

### 5.1 它和 ERD 的关系

完成规范化之后，把所有表（这里叫 3NF 表）之间的关系补出来，就得到**逻辑数据模型（logical data model, LDM）**。

它和 ERD 的关系可以这样理解：

| | ERD | 逻辑数据模型（LDM） |
| --- | --- | --- |
| 关注 | 业务概念与关系 | 具体的表、字段、键与关系 |
| 粒度 | 概念级 | 接近实现级，但仍不绑定具体产品 |
| 是否含类型长度 | 通常不含 | 含 |
| 是否含外键 | 不含 | 含 |

LDM 本身已经是一个关系模型（relational model）：表、字段、键、关系都明确了。再往后才是物理设计 —— 选具体的关系型数据库（relational database）、定索引、考虑分区。**LDM 阶段还在讲「逻辑」，还没到「用哪个产品、建什么索引」。**

### 5.2 参照完整性

LDM 里有个概念要提前留意 —— **参照完整性（referential integrity）**：外键指向的主键必须存在。它保证了「订单明细的父订单一定在」。

## 6 常见误区

- **以为规范化就是「表越多越好」。** 规范化的目标是消除冗余，不是增加表数。过度拆表会带来大量连接；
- **把派生字段当成普通字段存。** 见上面第 3 节；
- **跳过 1NF 直接讨论 3NF。** 重复组没拆掉的话，后面几步没有意义；
- **把 LDM 当成建表脚本。** LDM 还是逻辑模型，字段名可以更贴近业务。

## 8 术语表

| 术语 | 中文 | 一句话解释 |
| --- | --- | --- |
| normalization | 规范化 | 按规则调整表结构以消除冗余 |
| data redundancy | 数据冗余 | 同一份事实被存储在多个地方 |
| update anomaly | 更新异常 | 改一处漏一处导致数据互相矛盾 |
| insert anomaly | 插入异常 | 想录入某条信息却因缺少别的主数据而无法录入 |
| delete anomaly | 删除异常 | 删一条记录顺带丢失了别的信息 |
| multivalue attribute | 多值属性 | 一个单元格里塞了多个值 |
| repeating group | 重复组 | 同一组字段在同一记录里重复出现 |
| unnormalized form（UNF） | 未规范化形式 | 尚未套用任何规范化规则的原始表 |
| first normal form（1NF） | 第一范式 | 每格只放一个原子值，消除重复组 |
| second normal form（2NF） | 第二范式 | 非主键字段依赖整个主键，消除部分依赖 |
| third normal form（3NF） | 第三范式 | 非主键字段不依赖其他非主键字段 |
| functional dependency | 函数依赖 | 知道 A 就能唯一确定 B 的关系 |
| partial dependency | 部分依赖 | 只依赖复合主键中的一部分 |
| transitive dependency | 传递依赖 | 依赖了另一个非主键字段 |
| atomic value | 原子值 | 不可再分的最小数据单位 |
| derived attribute | 派生字段 | 可以由其他字段计算出来的字段 |
| optimization | 优化 | 出于性能考虑对规范化结果做的调整 |
| logical data model（LDM） | 逻辑数据模型 | 3NF 之上补齐字段、键与关系的模型 |
| relational model | 关系模型 | 以表与关系组织数据的模型 |
| referential integrity | 参照完整性 | 外键指向的主键必须存在 |
